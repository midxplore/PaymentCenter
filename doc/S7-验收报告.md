## 3. 本轮发现并修复的缺陷

### 3.1 ★ P0：`FOR UPDATE SKIP LOCKED` 导致并发下虚假「无可用收款账号」（会丢单）

**现象**：单账号、额度 1000 元（容量 33 笔）、单笔 30 元、**10 并发**，只有 **2 笔**成功，
其余 8 笔收到 `P1001「无可用收款账号」`——**而额度还剩 940 元**。

**根因**：预占语句写的是
`UPDATE ... WHERE Id = (SELECT ... ORDER BY 剩余 ASC LIMIT 1 FOR UPDATE SKIP LOCKED)`。

`SKIP LOCKED` 的语义是「跳过别人锁住的行，去选**下一个**候选」。设计时假设「同一 Type 下有多个候选账号」，
于是跳过一个还有下一个。但**商户单账号是常态**：唯一候选被跳过后，子查询返回空集 →
外层 `Id = (空)` → 更新 0 行 → 返回 `P1001`。

**为什么严重**：三方拿到「无可用收款账号」通常**不会重试**，等于直接丢单。
而且这个错误具有**误导性**——监控上看到的是「无可用账号」，会让人去查账号池，而真正原因是并发。

**决定性验证**（额度远大于需求，排除额度因素）：

| 实现 | 额度 1000 / 单笔 30 / 10 并发（容量 33 笔） | 额度 100 / 单笔 30 / 10 并发（容量 3 笔） |
|---|---|---|
| `FOR UPDATE SKIP LOCKED` | **2 / 10 成功** ❌ | 3 / 10（看似正确，实为巧合） |
| `FOR UPDATE`（阻塞等待） | **10 / 10 成功** ✅ | **3 / 10 成功** ✅ |

**修复**：`PayAllocateService.TryLockQuotaAsync` 的 SQL 改为阻塞式 `FOR UPDATE`。
后续请求排队等前一条语句提交，再在**外层 WHERE 上重新求值额度**——
额度够就成功，真不够才报 `P1001`，两个方向都正确。

**为什么等待是可接受的**：该语句刻意**在事务外**执行（见 `Allocate` 步骤 2），
锁的持有时间就是这一条 UPDATE 语句的执行时间（毫秒级），不存在长事务持锁排队。

**修复后回归**：F2 压测 66/66（修复前 56/66，10 项失败全部由此缺陷引起）。

> **教训**：`SKIP LOCKED` 不是「更好的并发写法」，它只是「不等」。
> 用在 `LIMIT 1` 的最佳适配查询上，等于把「等不到锁」错误地表达成了「没有候选」——
> 把一种**暂时性**状态渲染成了**终态**。凡是 `LIMIT 1` + 需要等待的语义，都不要用 `SKIP LOCKED`。

### 3.2 P1：订单号长度校验与列宽脱节（定时炸弹，约 2027-11 引爆）

**现象**：`pay_order.orderno` 等列早已按 `PayConst.OrderNoLength = 64` 建表
（因为雪花位数会随年份增长），但入参 DTO 上还写着 `[MaxLength(32)]`：

| 位置 | 问题 |
|---|---|
| `PayNotifyDto.cs` → `NotifyInput.OrderNo` | `[MaxLength(32)]` |
| `PayAbnormalDto.cs` → `LinkAbnormalInput.TargetOrderNo` | `[MaxLength(32)]` |

订单号格式是 `{yyyyMMddHHmmssfff}{雪花尾段}`，**2026 年正好 32 位**——
所以现在测不出来，是「刚好卡在上限」。约 **2027-11** 雪花尾段进位到 16 位后订单号变 **33 位**，
届时 `/api/pay/notify`（**所有到账通知**）与 `/api/payAbnormal/link`（人工关联）
会被参数校验整体挡下，且报的是参数错误而不是业务错误，排查成本高。

**修复**：两处上限改为 `PayConst.OrderNoLength`（与列宽同一个常量，不再各写一份）。

**回归守卫**（新增 2 条单元测试，谁再把数字写死就会失败）：
- `订单号相关的入参上限_必须等于列宽常量` —— 用反射读 `MaxLengthAttribute.Length` 与 `PayConst.OrderNoLength` 比对
- `订单号长度_必须为雪花进位留出余量` —— 断言 `当前长度 < OrderNoLength`（至少留 1 位）

### 3.3 测试工具缺陷（非产品）：签名 nonce 用毫秒时间戳导致并发撞 nonce

压测时 10 个并发请求在同一毫秒内拿到**相同 nonce**，被框架的重放检测判成 `401 重复的请求`，
表现为「N 个并发只有 1 个成功」——**伪装成产品的并发缺陷**，非常容易误判。

修复：`_pay_common.sign_call` 的 nonce 改用 `uuid4().hex`。
（同一问题也修了 `s6_admin_probe.py`。）

> **教训**：写并发回归脚本时，先确认**测试脚手架自身**在并发下是安全的——
> 否则会花大量时间去追一个根本不存在的产品 bug。

### 3.4 测试脚本自身的健壮性

- `s6_admin_probe.py` 的清理原先走 `docker exec psql`，依赖 docker 在 PATH 上；
  拿不到 docker 时**静默失败**（脚本继续跑，只是脏数据没清），下次跑时残留账号会抢走「最佳适配」，
  让断言凭空失败。已改为 psycopg2 直连，并在残留检查失败时**显式报 FAIL**（原先会静默跳过）。
- `pay_notify_regression.py` 的场景 8 原先**手工模拟**过期结转（自己在脚本里重写一遍算法）；
  已改为**走真实的过期作业** `PayOrderExpireJob`，验证的是生产路径。
