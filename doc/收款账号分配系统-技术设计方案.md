## 1. 总体思路

需求本质是「**资源池 + 额度记账 + 双写流水**」：

- **额度是唯一的稀缺资源**，全部正确性都压在"不能超发"上 → 并发方案是本设计的核心（§5.1）
- **两个写入源**（匹配预占 / 到账通知）会并发改同一条订单和同一个账号额度 → 用条件更新 + 状态守卫保证幂等与一致（§5.2）
- **流水只增不改** → 订单表冗余"当前状态"用于查询，另建事件表记录完整变更历史（§4.2）

设计原则：**能复用骨架的绝不自己写**。下面 §2 先盘清可复用的家底。

## 4. 数据模型

### 4.1 额度语义（本系统的地基）

账号上只存三个额度字段：

| 字段 | 含义 | 谁改 |
|---|---|---|
| `TotalQuota` | 总额度 | 管理员新增/追加（F1.1 / F1.2） |
| `UsedQuota` | 已用额度（累计**确认到账**） | 到账通知、订单过期 |
| `LockedQuota` | 锁定中额度（待到账/部分到账订单的**预占**） | 匹配成功时加，订单终结时减 |

```
剩余可用额度 = TotalQuota − UsedQuota − LockedQuota     ← 计算得出，不落库
```

> **不落库的理由**：落库就有三处数据可能不一致的风险。计算式查询成本可忽略（筛选条件里做减法即可）。

**额度结转的统一规则（贯穿 §5.2 / §5.3，请重点确认）：**

- **锁定永远按"请求金额"释放**：`LockedQuota -= RequestAmount`
- **已用永远按"实际到账金额"累加**：`UsedQuota += 本次到账`

这样订单完成时净扣减 = 实际到账额（超额到账也如实记账），订单过期时净释放 = 请求金额 − 已到账额，天然满足 F3.2「释放未达成部分的预占额度」。

索引：

- `(ClientId, ExternalNo)` **唯一** —— 幂等键。★ **必须是复合，不能只对 `ExternalNo` 建唯一索引**：
  单列唯一会让「A 用过 `EX-001`」导致 B 再传 `EX-001` 时命中 A 的订单，

> **不会删除**旧的单列唯一索引 `u_pay_order_en`。残留的旧索引会继续拒绝跨调用方的重复单号，

> 必须执行 `scripts/paycenter-schema.sql` 里的 `DROP INDEX IF EXISTS u_pay_order_en;`。

## 5. 核心流程设计

### 5.1 查询匹配 + 额度预占（F2）★最关键

**并发安全方案：PostgreSQL 单语句原子匹配（`FOR UPDATE SKIP LOCKED`）**

> **本小节为历史记录（原「条件更新 CAS + 有限重试」方案）**
>
> 迁移到 PostgreSQL 后已改为单语句原子匹配，**当前实现见下方「完整流程」步骤 2**。
> 保留本节是为了说明「列在左」这个写法的由来——它现在作为可移植约定继续生效，但 SQLite 前提已不成立。

原方案（已废弃）：

```sql
UPDATE pay_account
SET LockedQuota = LockedQuota + @amount, UpdateTime = @now
WHERE Id = @accountId
  AND Status = 1                                        -- 启用中
  AND TotalQuota >= UsedQuota + LockedQuota + @amount   -- 剩余够用
```

**判断依据：影响行数 == 1 才算锁定成功，== 0 说明被并发抢占。**

> ⚠️ **SQLite 亲和性陷阱（历史，2026-09-16 数据库已迁 PostgreSQL）**
>
> 上面条件**不能**写成直觉上更自然的 `TotalQuota - UsedQuota - LockedQuota >= @amount`。
> 原因：SqlSugar 把 `decimal` 参数按 `DbType.Decimal` 绑定，而 **Microsoft.Data.Sqlite 会把 decimal 存为 TEXT**；
> 同时 SQLite 的亲和性规则里**表达式没有亲和性**，于是「表达式 vs 无亲和性操作数」退化为按**存储类**比较——
> 而存储类序是 `NULL < INTEGER/REAL < TEXT < BLOB`，即 **REAL 永远小于 TEXT**。
> 结果：`(T - U - L) >= '30.00'` **恒为 false**，预占会彻底失效且不报任何错。
>
> 修正写法把带 NUMERIC 亲和性的**列**放在比较式一侧（`TotalQuota >= ...`），
> SQLite 便会对另一侧施加 NUMERIC 亲和性，比较恢复数值语义。
>
> 已实测对照（SQLite）：
>
> | 写法 | 结果 |
> |---|---|
> | `(TotalQuota - UsedQuota - LockedQuota) >= '30'` | ❌ 恒 false |
> | `TotalQuota >= (UsedQuota + LockedQuota + '30')` | ✅ 正确 |
> | `LockedQuota >= '30'`（列在左） | ✅ 正确 |
>
> **约定（继续有效）**：本系统所有涉及金额的比较条件，一律让**列出现在比较式一侧**。
> 迁到 PG 后该坑不再触发，保留写法是为了可移植（MySQL/PG 语义等价）与可读性。

> **为什么不用 CAS 循环（2026-09-16 变更）**：原设计是「先 SELECT 候选、再逐个 CAS 条件更新、最多 3 轮 × 10 候选」，
> 迁到 PostgreSQL 后改为**单语句原子匹配** `UPDATE ... WHERE Id = (SELECT ... FOR UPDATE LIMIT 1)`。
> 原因：CAS 写法在 SELECT 与 UPDATE 之间存在时间窗口，并发请求会挑中同一行、抢输后重试，于是
> ①「最佳适配」从硬保证退化为尽力而为；② 候选批次耗尽时会**误报 P1001「无可用收款账号」**，即使池中仍有额度。
> 单语句原子匹配把「选行」与「加锁」放进同一条语句，窗口与重试都不存在了。
> （原「SQLite 不支持 `SELECT ... FOR UPDATE`」的理由已随数据库迁移失效。）

> ⚠️ **必须用阻塞式 `FOR UPDATE`，不能用 `FOR UPDATE SKIP LOCKED`（2026-09-17 修正）**
>
> 迁移时曾写成 `FOR UPDATE SKIP LOCKED`，理由是「跳过被锁的行、去选下一个最优候选」。
> **这个理由只在「同一 Type 下有多个候选账号」时才成立**。一旦某 Type 只有**一个**可用账号
> （商户单账号是常态），并发请求会把这个唯一候选跳过去 → 子查询返回空集 →
> 外层 `Id = (空)` → 更新 0 行 → 调用方收到 `P1001「无可用收款账号」`，
> **而账号额度其实还剩很多**。三方拿到这个错误通常不会重试，等于**丢单**。
>
> 实测（单账号、额度 1000、单笔 30、10 并发，容量 33 笔远大于并发数）：
>
> | 实现 | 成功笔数 | 结论 |
> |---|---|---|
> | `FOR UPDATE SKIP LOCKED` | **2 / 10** | 失败与额度无关，是锁被跳过 → 虚假 P1001 |
> | `FOR UPDATE`（阻塞等待） | **10 / 10** | 排队后重新求值额度，全部正确受理 |
>
> 阻塞式 `FOR UPDATE` 的等待是**有界**的：本方法刻意在**事务外**执行（见下方完整流程步骤 2），
> 锁的持有时间就是这一条 UPDATE 语句的执行时间（毫秒级），不存在长事务持锁排队的问题。
> 而「等到锁之后必须重新求值额度」正是外层 WHERE 再判一次额度这条的存在意义——
> 它同时挡住了「超发」和「虚假无可用」两个方向的错误。

**匹配算法（F2.2 最佳适配）**：

候选排序 `ORDER BY (TotalQuota - UsedQuota - LockedQuota) ASC, CreateTime ASC`

- 在"剩余 ≥ 请求金额"的约束下，**最小化剩余 = 最小化 |剩余 − 金额|**，即最佳适配
- 剩余相同时按 `CreateTime ASC`，保证规则确定可复现（F2.2 明确要求）

**完整流程**：

```
入参：Type, Amount, ExternalNo?

1. 幂等前置检查（F2.6）
   clientId = PayCallerContext.RequireClientId()   -- 解析不到直接抛错，不要退化成 0
   if ExternalNo != null:
       查 pay_order WHERE ExternalNo = ? AND ClientId = ?  →  命中则直接返回该订单，不再匹配

2. 单语句原子预占（事务外，锁定即生效）
   UPDATE pay_account
      SET LockedQuota = LockedQuota + @amount,
          Status      = CASE WHEN TotalQuota <= UsedQuota + LockedQuota + @amount
                             THEN @exhausted ELSE Status END,   -- F1.4 额度耗尽同语句下架
          UpdateTime  = @now
    WHERE Id = (
           SELECT Id FROM pay_account
            WHERE Type = @type AND Status = @enabled AND IsDelete = false
              AND TotalQuota >= UsedQuota + LockedQuota + @amount
            ORDER BY (TotalQuota - UsedQuota - LockedQuota) ASC, CreateTime ASC
            LIMIT 1 FOR UPDATE)          -- ★ 阻塞等待，不要加 SKIP LOCKED
      AND Status = @enabled AND IsDelete = false
      AND TotalQuota >= UsedQuota + LockedQuota + @amount   -- ★ 等到锁后重新求值额度
   RETURNING Id

   返回 0 行 → 返回"无可用账号"（F2.5），不生成订单

3. 锁定成功，开启事务：
   3.1 生成 OrderNo（自包含雪花生成，见下方备注）
   3.2 INSERT pay_order（Status = 待到账，ExpireTime = now + 全局配置时长，
                         ClientId = 步骤 1 解析出的调用方）
   3.3 INSERT pay_order_event（EventType = 创建）
   3.4 INSERT pay_audit_log（action = ApiCall，与业务变更**同事务**，记录「是哪个调用方发起的」）
   3.5 COMMIT

   ⚠️ 若 3.2 因 (ClientId, ExternalNo) 唯一索引冲突失败（同一调用方并发同单号）：
       回滚事务 → 释放步骤 2 的预占 → 返回已存在的那笔订单

4. 返回：订单号、账号信息、过期时间
```

**要点说明**：

- **幂等键必须按调用方隔离**：唯一索引是 `(ClientId, ExternalNo)` 复合，查询也必须带 `ClientId`。
  查询只有**一处实现**（`PayAllocateService.FindByIdempotencyKeyAsync(clientId, externalNo)`），
  避免「某个分支忘了加 ClientId」这种改一半的形态。
- **`ClientId` 的解析不允许 `?? 0` 兜底**：退化成 0 会让所有接入方共享同一个「0 号调用方」的去重命名空间 ——
  A 用过的凭证号会把 B 的到账通知**静默去重**掉（钱被吞、双方都看不到报错）。
  解析不到就抛错：签名鉴权上下文缺失意味着该接口没被签名保护，是配置错误，不该被容忍。
- **审计与业务变更同事务**：`ApiCall` 审计行写在同一个 `ISqlSugarClient` 事务里。
  若分开写，一旦审计失败就可能出现「钱动了但没人知道是谁动的」，而这正是审计要回答的问题。
- **`GetStatus` 必须带归属校验**：`WHERE OrderNo = ? AND ClientId = ?`，
  且「查无此单」与「不是你的单」返回**同一个** `P1004`，否则该接口会变成订单号的存在性探针。

- 步骤 2 在事务外执行，锁定即生效；步骤 3 若失败必须补偿释放（`LockedQuota -= amount`），否则额度会泄漏
- 步骤 2 的状态置位与额度扣减**必须在同一条语句里**（上面的 `CASE`）。
  若拆成「先锁定、再由调用方补一次状态同步」，两者之间就有窗口：该账号在窗口内仍是「启用」且剩余为 0，
  破坏「启用 ⇒ 剩余 > 0」这条不变量
- **取号改为自包含雪花生成（2026-09-17 落地，`PayOrderNoGenerator`，F2.3 方案 B）**

> **取号设计（已落地）**
>
> 订单号 = `{yyyyMMddHHmmssfff}{雪花Id}`，纯数字、日期前置，形如
> `20260917003919923849439776370757`（当前 32 位）。
>
> - **前 17 位是生成时刻**（`yyyyMMddHHmmssfff`）：三方（银行 / 支付渠道）拿到订单号即可
>   直接按日期检索、在流水文件里做前缀匹配，不需要先解析雪花时间戳
> - **尾段是框架已注册的 `YitIdHelper.NextId()`**（`SqlSugarSetup.AddSqlSugar` 里
>   `services.AddYitIdHelper(...)` + `StaticConfig.CustomSnowFlakeFunc`，实体主键本来就在用）：
>   时间戳 + WorkId + 序列号三段，**跨进程、跨重启全局唯一**
> - 无业务前缀，纯数字，便于三方流水文件里直接做字符串匹配
> - 取号是**纯内存操作**：不碰数据库、不加锁、无 IO，可在事务外调用
> - 订单号按时间单调递增（同长度下字符串序 == 时间序），三方直接排序即可
>
> **走过的两条弯路（都已废弃，原因不同）**：
>
> 1. **`SysSerial.NextSeqNo(type, isGlobal: true)` 逐号取**——每次取号先抢一把**分布式锁**，
>    实测 ≤20 并发 100% 成功、**30 并发起大量失败**（锁等待超时抛「服务正忙，请稍后再试！」）。
>    这是**可用性缺陷**（取不到号的订单直接失败），不是性能问题，加重试只是打补丁。
> 2. **号段批量预取（Leaf-segment）**——一条语句从 `sysserial` 原子领走一段序号缓存在进程内。
>    并发问题解决了，但仍在 `sysserial` 上挂着一份配置与租户上下文依赖：
>    换数据库要带种子、改格式要走后台、拆分模块要连表一起搬。
>
> **为什么最终选方案 B（自包含）**：本模块要能**整体拆出去独立部署**。
> 现在只用框架的**库**（`Yitter.IdGenerator`，实体主键本来就在用），
> 不依赖框架的**表与后台配置**——`sysserial` 里不再有 `pay_order` 类型，种子也已移除。
>
> **代价与对策**：订单号变长（32~33 位，且雪花位数随年份增长，约 2027-11 起由 15 位变 16 位）。
> 因此 `pay_order.orderno`、`pay_order_event.orderno`、`pay_notify_record.orderno`、
> `pay_abnormal_receipt.reportorderno` / `relatedorderno` 统一按 `PayConst.OrderNoLength = 64` 建表，一次留足余量。

### 5.2 异步到账通知（F4）

单事务内完成，**所有状态变更都带条件守卫**，保证与过期任务、其他通知并发时不出错：

```
入参：OrderNo, Amount, NotifyTime, VoucherNo

1. 凭证号去重（F4.5）
   INSERT pay_notify_record (ClientId, VoucherNo, ...)
   唯一索引冲突 → 返回"重复通知，已忽略"，不累加金额   ← 先插后判，靠 DB 保证

2. 查订单 WHERE OrderNo = ?
   找不到 → 写 pay_abnormal_receipt(Reason = 无匹配订单)（F5.1）→ 返回

3. 订单终态判断
   Status == 已过期  → 写异常台账(Reason = 已过期)（F3.3）→ 返回
   Status == 已完成  → 写异常台账(Reason = 订单已完成) → 返回

4. 累加到账金额（带状态守卫的 CAS，防与过期任务并发）
   UPDATE pay_order
   SET ReceivedAmount = ReceivedAmount + @amount
   WHERE Id = @id AND Status IN (待到账, 部分到账)
   影响行数 == 0 → 说明订单刚被过期任务终结 → 写异常台账 → 返回

5. 判定新状态
   新累计 >= RequestAmount（F4.2）：
       UPDATE pay_order SET Status = 已完成, CompleteTime = now WHERE Id = @id
       UPDATE pay_account
       SET UsedQuota = UsedQuota + @amount,        -- 已用按实际到账
           LockedQuota = LockedQuota - @requestAmount   -- 锁定按请求金额释放
       WHERE Id = @accountId
       若 @amount > 本次应补金额 → 在 OverpayRemark 记差额（F4.4）

   新累计 < RequestAmount（F4.3）：
       UPDATE pay_order SET Status = 部分到账 WHERE Id = @id
       （额度继续锁定，不动 UsedQuota / LockedQuota）

6. INSERT pay_order_event（部分到账 / 完成）

7. 返回：处理结果 + 当前订单状态 + 累计到账金额（F4.6）
```

### 5.3 订单自动过期（F3.2）

新增定时任务 `PayOrderExpireJob`，**每分钟**执行（触发器用 `[Minutely]`）：

```
1. 扫描：SELECT * FROM pay_order
        WHERE Status IN (待到账, 部分到账) AND ExpireTime < now
        LIMIT 200          -- 分批，避免长事务

2. 逐条处理（每条一个独立事务）：
   2.1 条件更新订单状态（防与并发的到账通知抢）
       UPDATE pay_order SET Status = 已过期
       WHERE Id = @id AND Status IN (待到账, 部分到账)
       影响行数 == 0 → 已被到账通知终结，跳过

   2.2 结转额度
       UPDATE pay_account
       SET UsedQuota   = UsedQuota   + @receivedAmount,      -- 已到账部分转已用
           LockedQuota = LockedQuota - @requestAmount        -- 释放全部预占
       WHERE Id = @accountId
       → 净释放 = 请求金额 − 已到账金额（部分到账场景）
       → 全额释放（未到账场景，@receivedAmount = 0）

   2.3 INSERT pay_order_event（过期）

3. 记录本次过期数量到日志
```

> 任务用 `[JobDetail(Concurrent = false)]` 保证同一时刻只有一个实例在跑。

#### 5.3.1 落地实现（2026-09-17）—— ✅ 已完成

| 事项 | 做法 |
|---|---|
| 调度 | **复用骨架作业调度**：`[JobDetail(PayConst.ExpireJobId, Concurrent = false)]` + `[Minutely(TriggerId = ...)]`，照 `CleanSysLogJob` 写。作业被自动发现并持久化到 `sysjobdetail` / `sysjobtrigger`，可在后台「任务调度」页面查看与手工执行 |
| 逻辑位置 | 业务逻辑在 `PayOrderExpireService`，作业只做「取 scope → 调服务」。这样过期逻辑可脱离调度器测试（否则只能等一分钟跑一次） |
| 事务粒度 | **每条订单一个独立事务**（`_db.AsTenant().BeginTran()`），单条失败只记日志、不影响同批其它订单，下一轮扫描还会捞到它 |
| 分批 | `PayConst.ExpireScanBatchSize = 200`，按 `ExpireTime` 升序（积压时最早的欠账优先清掉） |
| 额度释放后 | 调 `PayAccountService.SyncStatusByQuotaAsync`：预占释放可能让「已用完」的账号剩余额度恢复为正，需自动回到「启用」重新参与匹配（F1.4） |

**★ 一个必须写对的顺序：先抢占状态，再读到账金额**

```
❌ 先读到账金额 → 再抢占状态
  两次读取之间，到账通知可能已把金额加上去（它的累加语句与这里的抢占是同一行的两次条件更新），
  过期任务就会按偏小的旧值结转 → UsedQuota 少记、LockedQuota 多释放（账实不符）

✅ 先条件抢占（WHERE Status IN (待到账,部分到账) AND ExpireTime <= now）
  → 抢占成功即意味着到账通知再也改不动这行 → 此时再读，读到的是「冻结后」的准确金额
```

**「变更前状态」怎么还原**：抢占成功后状态已是「已过期」，但抢占条件已保证它此前 ∈ {待到账, 部分到账}，
而到账金额 > 0 ⟺ 部分到账（金额必须 > 0，零元到账进不来），据此还原写进事件流水。

**事件备注的分支依据是「有没有收到过到账」，不是「释放额是否为正」**：
未到账时释放额恰好等于请求金额（也是正数），用释放额判会走错分支（此坑由单元测试抓出）。

```
入参：AbnormalId, TargetOrderNo
```

订单已过期/已完成的场景，正确做法是**重新走匹配接口下新单**，再把该笔到账关联到新单上

（`Applied` 是派生状态，`PayNotifyRecord` 的类注释已明确允许回填。）

## 6. 订单状态机

```
                    ┌──────────────┐
   匹配成功、预占额度  │   待到账     │
   ─────────────────>│  (Pending)   │
                    └──────┬───────┘
                           │
              到账 < 请求金额 │  到账 ≥ 请求金额
                           │
              ┌────────────┴────────────┐
              ▼                         ▼
       ┌──────────────┐         ┌──────────────┐
       │  部分到账    │────────>│   已完成     │
       │  (Partial)   │ 累计达标 │ (Completed)  │
       └──────┬───────┘         └──────────────┘
              │                 额度：Used += 实际到账
              │ 超过过期时长            Locked -= 请求金额
              ▼
       ┌──────────────┐
       │   已过期     │
       │  (Expired)   │
       └──────────────┘
       额度：Used += 已到账
             Locked -= 请求金额（净释放未达成部分）
```

- **已完成 / 已过期是终态**，不可逆
- 终态后再收到到账通知 → 进异常台账，**不改订单**（F3.3）

**请求**
```json
{
  "type": "wxpay",              // 收款类型，必填
  "amount": 128.50,             // 收款金额，必填，> 0
```

### 7.3 订单状态查询接口

```

鉴权：Signature（需 scope = allocate）
```

> 原稿写的是 `GET /api/pay/order/{orderNo}`。实际采用查询串形式：Furion 动态 API 的
> 路由段由「控制器名 + 方法名」生成，`GetStatus` 落在 `/api/pay/status`；
> 路径参数形式需要单独写 `[Route]`，与「尽量用框架约定、少写自定义路由」相冲突，
> 因此以查询串形式为准（契约以本节为准）。

**归属校验（2026-09-17 补）**：查询必须带调用方归属 —— `WHERE OrderNo = ? AND ClientId = ?`。
「查无此单」与「不是你的单」返回**同一个** `P1004`，否则该接口会退化成订单号的存在性探针。
同时显式声明 `[PayScope(PayConst.ScopeAllocate)]`，不再依赖路径兜底匹配。

> **为什么 allocate 侧要隔离、notify 侧不隔离**：`allocate` 由业务系统调用 —— 订单是它创建的，
> 它拥有这些订单，必须隔离；`notify` 由支付渠道调用 —— 渠道**不创建订单**，
> 若按 ClientId 过滤，所有到账通知都会找不到订单而掉进异常台账。
> 两侧的信任模型不同，不能照抄。渠道侧的补偿控制是：该凭证只授 `scope=notify`，且每次调用都落审计。

## 8. 鉴权与权限分离（F6）

### 8.1 签名方案（复用 `SignatureAuth`）

骨架已实现，**不需要自己写**：

| 请求头 | 说明 |
|---|---|
| `accessKey` | 接入方身份标识 |
| `timestamp` | 时间戳（秒或毫秒，自动识别） |
| `nonce` | 唯一随机数 |
| `sign` | HMAC-SHA256(secret, `{METHOD}&{Path}&{accessKey}&{timestamp}&{nonce}`) → Base64 |

已内置：时间偏差校验（超出直接拒）、nonce 重放检测（走缓存）、`GetAccessSecret` 回调取密钥。

**接入方式（✅ 已落地）**：对外接口挂

```csharp
[Authorize(AuthenticationSchemes = SignatureAuthenticationDefaults.AuthenticationScheme)]
```

不需要自己写签名校验，也不需要 `[AllowAnonymous]`。实测该特性可正确覆盖
`AddJwt(enableGlobalAuthorize: true)` 注册的全局 JWT 授权过滤器，签名请求会走
`SignatureAuthenticationHandler`，失败原因经框架既有的 `AuthenticateFailMsgKey` 通道
透传到 401 响应：

| 场景 | 响应 |
|---|---|
| 无任何鉴权头 | `401 accessKey 不能为空` |
| 未知 accessKey | `401 accessKey 无效` |
| 签名错误 | `401 sign 无效的签名` |
| 同一 nonce 重放 | 首次 200，第二次 `401 重复的请求` |

### 8.2 权限分离（F6.2）—— ✅ 已落地

**问题**：`SysOpenAccess` 表原本只有 `AccessKey` / `AccessSecret` / 绑定用户租户，**没有权限范围字段**，无法区分「只能查匹配」和「能报到账」。

**实现**：给 `SysOpenAccess` 增加 `Scopes` 字段（逗号分隔，如 `allocate,notify`）。
因为 `AddOpenAccessInput` / `OpenAccessOutput` 都继承 `SysOpenAccess`，后台管理接口自动带上该字段，无需逐个改 DTO。

```csharp
/// <summary>
/// 权限范围（逗号分隔，如 allocate,notify；留空表示不限制）
/// </summary>
[SugarColumn(ColumnDescription = "权限范围", Length = 128, IsNullable = true)]
[MaxLength(128)]
public virtual string Scopes { get; set; }
```

**校验位置**：在框架既有的 `SysOpenAccessService.GetSignatureAuthenticationEventImpl()`
的 `OnValidated` 事件里做——即**改框架的事件实现，而不是另写一套鉴权 handler**。

规则本身由业务提供，通过 Core 留出的钩子注入（Core 不能反向依赖业务程序集）：

```csharp
// Admin.NET.Core/SignatureAuth/IOpenAccessScopeResolver.cs —— 框架留钩子
public interface IOpenAccessScopeResolver
{
    string ResolveRequiredScope(HttpContext context);   // 返回所需 scope；null/空 = 不限制
}

// Admin.NET.Application/PayCenter/Auth/PayScope.cs —— 业务填增量
[AttributeUsage(AttributeTargets.Method)]
public class PayScopeAttribute : Attribute { public string Scope { get; } ... }

public class PayScopeResolver : IOpenAccessScopeResolver, ISingleton
{
    public string ResolveRequiredScope(HttpContext context) =>
        context.GetEndpoint()?.Metadata.GetMetadata<PayScopeAttribute>()?.Scope;
}
```

接口上就近声明所需 scope（改接口时不会忘记同步权限规则）：

```csharp
[PayScope(PayConst.ScopeAllocate)] public Task<AllocateOutput> Allocate(...)
[PayScope(PayConst.ScopeNotify)]   public Task<NotifyOutput>   Notify(...)
```

**失败关闭（fail-closed）**：`Scopes` 为空的密钥视为「未授权任何接口」而拒绝，
而不是放行。理由——这些接口直接关联资金，升级后宁可让接入方看到一条明确的
`401 accessKey 未配置权限范围，拒绝访问（需要 scope=allocate）`，也不能因为配置遗漏把接口默认敞开。

**实测矩阵**：

| 密钥 scopes | 访问 `/api/pay/allocate` | 访问 `/api/pay/notify` |
|---|---|---|
| （空） | `401 未配置权限范围` | `401 未配置权限范围` |
| `allocate` | ✅ 进入业务 | `401 无权访问该接口（需要 scope=notify，已授权 allocate）` |
| `allocate,notify` | ✅ 进入业务 | ✅ 进入业务 |

> ⚠️ **运维注意**：`SysOpenAccess` 走 `SysCacheService` 缓存（key `CacheConst.KeyOpenAccess + accessKey`）。
> 通过后台管理接口改 `Scopes` 会自动清缓存；**直接改数据库不会**，需等缓存过期或重启服务。
>
> 为什么扩展 `SysOpenAccess` 而不是新建表：能直接复用现成的密钥管理界面、缓存逻辑和签名回调，改造量最小。

### 8.3 敏感信息脱敏（F6.4）—— **已确认：不做脱敏**

需求写的是「账号/收款码等敏感信息在接口返回及后台展示时按权限脱敏」，但这里有内在矛盾：

- 业务调用方拿账号的**唯一目的就是去收款**，如果接口返回脱敏后的账号，调用方无法完成收款
- 后台要**维护账号信息**（新增、编辑、核对），脱敏后无法维护

**已拍板方案（2026-09-16 确认）**：

| 场景 | 处理 |
|---|---|
| 对外接口（allocate） | 返回**完整**账号信息（调用方已通过签名鉴权，是可信方） |
| 后台列表 / 详情 / 编辑 | **同样返回完整值**，不做脱敏（需维护账号信息） |
| 日志 / 事件流水 | 一律不落账号明文，只落 AccountId |

> 因此 `PayMaskUtil` 与 `PayConst.MaskKeepPrefix/MaskKeepSuffix` 均**不实现**，已从代码中移除。
> 账号明文的保护改由「接口签名鉴权 + 后台 RBAC 菜单/按钮权限」承担。

### 8.4 签名失败告警（F6.5）—— ✅ 已落地

**先纠正一个前提**：原方案写的是「复用 `AdminNETResultProvider` 已有签名失败日志」，
但核对代码后确认**骨架里并不存在这样的日志**：

| 位置 | 实际行为 |
|---|---|
| `AdminNETResultProvider.OnResponseStatusCodes` | 只把失败原因写进 **401 响应体**（读 `AuthenticateFailMsgKey`），**不落任何日志** |
| `SignatureAuthenticationHandler.AuthenticateResultFailAsync` | 只把消息塞进 `HttpContext.Items`，不落日志 |
| `LoggingMonitor` → `SysLogOp` | 采集不到——**401 发生在 MVC 之前**，请求根本没进控制器 |
| `SysOpenAccessService.OnGetAccessSecret` | 只在**查询抛异常**时 `LogError`；「accessKey 不存在」是正常返回空串，不记日志 |

实测印证：反复触发匿名 / 未知 key / 错签名 / scope 越权后，`syslogop` 里 0 条 401 记录
（全部 21 条均为业务成功调用，`status=200`）。

**落地方式**：在框架既有的 `SignatureAuthenticationEvent.OnChallenge` 钩子里补一条告警
（同 F6.2 的思路——**填框架留的钩子，不新写中间件**）。选 `OnChallenge` 的理由：
失败原因（含 scope 越权）此时已完整可得，且只在真正返回 401 时触发，不会重复记。

```csharp
// Admin.NET.Core/Service/OpenAccess/SysOpenAccessService.cs
OnChallenge = context =>
{
    if (context.AuthenticateFailure != null)
    {
        var logger = context.HttpContext.RequestServices.GetRequiredService<ILogger<SysOpenAccessService>>();
        logger.LogWarning(
            "开放接口签名校验失败：{Reason}｜accessKey={AccessKey}｜{Method} {Path}｜remoteIp={RemoteIp}",
            context.AuthenticateFailure.Message,
            context.HttpContext.Request.Headers["accessKey"].FirstOrDefault() ?? "<空>",
            context.HttpContext.Request.Method,
            context.HttpContext.Request.Path.Value,
            context.HttpContext.Connection.RemoteIpAddress);
    }
    return Task.CompletedTask;
}
```

**实测输出**（每条失败都留痕，含来源 IP）：

```
开放接口签名校验失败：accessKey 不能为空｜accessKey=<空>｜POST /api/pay/allocate｜remoteIp=::1
开放接口签名校验失败：accessKey 无效｜accessKey=probe_unknown｜POST /api/pay/allocate｜remoteIp=::1
开放接口签名校验失败：sign 无效的签名｜accessKey=probe_ak_noscope｜POST /api/pay/allocate｜remoteIp=::1
开放接口签名校验失败：accessKey 未配置权限范围，拒绝访问（需要 scope=allocate）｜accessKey=...｜POST /api/pay/allocate｜remoteIp=::1
```

> 级别取 `Warning`：签名失败既可能是密钥被爆破（安全事件），也可能只是接入方签名算法写错（配置问题），
> 两者都值得被日志聚合规则捕获。接入方上线前可用这条日志自查签名串是否拼对。
> 更进一步的「失败次数阈值触发通知」不在本期范围。

### 8.6 鉴权与审计加固（2026-09-17）—— ✅ 已落地

一次针对「对外接口认证严格性 + 审计完整性」的专项加固。逐条列出**问题 → 修法**，
因为每一条都对应一个「不报错但会静默出错」的形态。

#### 8.6.1 传输层与凭证

| 问题 | 修法 |
|---|---|
| HMAC 比较用 `!=`（短路比较，耗时随公共前缀变化 → timing oracle） | 改 `CryptographicOperations.FixedTimeEquals` |
| `SysOpenAccess` 没有状态字段 → 吊销只能删行，会让 `pay_order.ClientId` / 审计引用悬空 | 加 `Status`（`StatusEnum`）；`OnGetAccessSecret` 对停用凭证返回**空密钥**，对外与「accessKey 无效」**不可区分**（不泄漏「该 key 存在但被停用」） |
| `sysOpenAccess/page` 明文回显全部接入方密钥 | `OpenAccessOutput.AccessSecret` 在 **getter 层**脱敏（`OpenAccessSecretMask.Mask`）→ 任何查询/投影都绕不过。掩码 `****`（`*` 不在 Base64 字符集 → 「含 `*`」无歧义地表示「这是掩码」） |
| 编辑弹窗把掩码当密钥回写 | 「掩码 = 不改」：`UpdateOpenAccessInput` **不再继承** `AddOpenAccessInput`（基类 `[Required]` 会让「掩码=不改」永远走不到）；留空或回传自身掩码 → 保留原值；含 `*` 的其它值 → 拒绝 |
| 改 `AccessKey` 后旧 key 仍凭缓存通过 | 同时清除新旧两个 key 的缓存条目 |
| `/api/pay/*` 无专属限流，兜底规则形同虚设 | `Limit.json` 增加 `/api/pay/*` 规则（1s/100、1m/2000），**必须排在兜底 `*` 规则之前**（AspNetCoreRateLimit 首条匹配） |

#### 8.6.2 业务层越权

| 问题 | 修法 |
|---|---|
| 幂等键 `ExternalNo` 未按调用方隔离 → A 的 `externalNo` 命中 B 的订单，泄漏 OrderNo + 完整收款账号 | 唯一索引改 `(ClientId, ExternalNo)` 复合；查询只有一处实现 `FindByIdempotencyKeyAsync`；DDL 必须 `DROP INDEX u_pay_order_en`（CodeFirst 不删旧索引） |
| `GetStatus` 无归属校验 → 任何有效密钥可读任意订单 | `WHERE OrderNo = ? AND ClientId = ?`；「查无此单」与「不是你的单」同返 `P1004` |
| `GetStatus` 未声明 `[PayScope]` | 补 `[PayScope(ScopeAllocate)]` |
| `PayScopeResolver` 对未归类 `/api/pay*` 路径返回 `null`（= 不限制）→ 新接口忘写 `[PayScope]` 就默认敞开 | 改返回 `PayConst.ScopeUnclassified`（**fail-closed**） |
| `notify` 里 `clientId ?? 0` 兜底 → 所有接入方共享「0 号调用方」去重命名空间，A 的凭证号会静默去重掉 B 的到账通知 | 改 `PayCallerContext.RequireClientId()`，解析不到即抛错 |
| `ClientId` 解析在两个 Service 里各写一份 | 收敛到 `PayCenter/Auth/PayCallerContext`（单一来源） |
| 两个凭证管理接口（`sysOpenAccess/secret`、`generateSignature`）没有任何按钮权限 | 补 Core 菜单种子 Btn 行。★ **权限串必须是路由尾部，而路由不等于方法名**：`CreateSecret` 的路由是 `/api/sysOpenAccess/secret`，照方法名写会永远匹配不上 |
| 另有 4 个 PayCenter 接口无按钮权限（`detailByNo` / `exportNotify` / `typeOptions` / `statusOptions`） | 补 `PayMenuSeedData` Btn 行。其中 `detailByNo`（按单号取全量详情）与 `exportNotify`（导出全部到账流水）是**真敞口** |

> **根因（务必记住）**：框架鉴权是**黑名单**模型 ——
> `SysRoleService.GetUserApiList` 里 `apiList[1] = 全部按钮 − 用户已有按钮`，
> `JwtHandler` 判定 `path.EndsWith(permission)`：路径匹配得上某个 permission 才可能被拦，
> **匹配不上任何 permission 就落进「不在黑名单」→ 放行**。
> 所以「漏挂权限」不会报错，只会让接口对**任何已登录用户**开放。
> 守卫 `pay_schema_guard.py` §8 已把 `/api/pay*` 全部后台接口与两个 `sysOpenAccess` 按钮纳入断言。

#### 8.6.3 审计完整性

401 发生在 **MVC 之前**，`LoggingMonitor` / `SysLogOp` 采集不到（实测 `syslogop` 里 0 条 401），
且 `SysLogOp` 会被 `CleanSysLogJob` 按保留期清理 —— 不能作为「永久可查」的审计。

**两条线**：

| 线 | 落点 | 要点 |
|---|---|---|
| 认证失败 | Core 新增 `IOpenAccessAuditSink` 钩子；`SysOpenAccessService.OnChallenge` 逐个 sink `try/catch` 广播；业务侧 `PayOpenAccessAuditSink` 落 `pay_audit_log(action=ApiAuthFailure)` | sink **必须吞掉所有异常**（审计不可用不能把 401 变成 500）；**只记带 accessKey 的失败**（匿名请求无主体可归属，记录等于给攻击者零成本刷表）；写入前按列宽截断（否则超长报错被自己的 catch 吞掉 → 静默丢审计） |
| 资金动作 | `PayAuditService.WriteOpenApiAsync(...)` 写 `action=ApiCall` | 与业务变更**同事务**（`allocate` 建单 + `notify` 各分支）；只读的 `status` **不审计**（避免轮询刷表） |

`pay_audit_log` 新增 `clientid bigint` + `clientkey varchar(128)`：
`OperatorId` 是 `sysuser.id`，与 `sysopenaccess.id` **不同命名空间**，复用会污染「按操作人查审计」；
`ClientKey` 存原始 accessKey 让审计行**自包含**（凭证行可能被删、认证失败的 key 可能根本不存在）。
开放接口行的 `OperatorId = 0`、`OperatorName = 开放接口`。

**新增枚举**：`PayAuditActionEnum.ApiCall = 8`、`ApiAuthFailure = 9`。

> 为什么不复用 `pay_order_event`：它回答「订单发生了什么」，审计要回答「**是谁**让它发生的」。

#### 8.6.4 前端配套

| 文件 | 改动 |

#### 8.6.5 入参 DTO 的校验不变式 —— ✅ 已落地

凭证管理面的两个「静默失效」缺陷，都在**不报错**的前提下让校验形同虚设。
两条都已修，并写进守卫脚本 §10 防止回退。

**（1）`[Required]` 挂在非空值类型上等于没写**

`RequiredAttribute.IsValid` 只判 `value is null`，而 `long` / `int` / `enum` 装箱后永远不为 `null`，
所以 `[Required] public long BindUserId` 的校验**恒为通过**。后果不是「少一道校验」，而是
`BindUserId = 0` 的凭证被建出来之后，`OnValidated` 里 `openAccess.BindUser.Account` 会因
`BindUser` 为 `null` 抛 NRE —— 该 accessKey 的**每一次**调用都变成 500。

改法：一律换成 `[Range(1, long.MaxValue, ErrorMessage = "…不能为空")]`。
涉及 `AddOpenAccessInput` / `UpdateOpenAccessInput` 的 `BindUserId` / `BindTenantId`，
以及 `GenerateSignatureInput.Timestamp`（原来的 `[Required]` 是空操作，
传 `timestamp=0` 会被放行，然后算出一个永远不可能通过校验的签名，使用者只会看到「签名不对」）。

**（2）入参 DTO 继承实体会让基类的校验特性漏进来**

`DataAnnotations` 的特性是 `Inherited = true`，`override` 属性会**沿重写链继承基类同名属性上的特性**
（`TypeDescriptor` 会把基类属性的特性合并进来）。于是：

| 版本 | 写法 | 结果 |
|---|---|---|
| 最初 | `UpdateOpenAccessInput : AddOpenAccessInput` | 被 `AddOpenAccessInput` 的 `[Required]` 挡下 |
| 中间（一次不彻底的修） | `UpdateOpenAccessInput : SysOpenAccess` | **依然被挡下** —— 实体 `SysOpenAccess.AccessSecret` 上也有 `[Required]` |
| 现在 | `UpdateOpenAccessInput` **不继承任何类型**，字段全部平铺 | 只有 `accessKey` 必填 |

**识别特征**：报的是默认**英文**文案 `The AccessSecret field is required.`。
本类没有写过英文消息，看到英文默认文案就说明它来自继承链上游而不是本类。

**为什么这是安全问题而不只是体验问题**：编辑弹窗的既定语义是「密钥留空 / 保持掩码 = 不修改」
（前端 `secretRules` 在编辑态返回 `[]`、placeholder 也这么写）。若服务端把它标成必填，
该语义就永远走不到服务端，而运维**停用一把泄漏的密钥**时会被迫回填密钥明文。

**顺带修掉的一个隐患**：`UpdateOpenAccessInput.Status` 现在是**可空**的，`null` = 不修改。
不能给它 `= StatusEnum.Enable` 这种默认值 —— 那会让「只改 scopes、没带 status」的请求
**静默把一把已停用的凭证重新启用**。停用是密钥泄漏时的止血手段，
不能存在任何「不显式声明就能把它关掉」的路径。

#### 8.6.6 「停用即失效」的端到端验证 —— ✅ 已落地

`scripts/pay_openaccess_gate_probe.py`（20 项断言）补齐了此前只有静态证据的一条控制：
**把 accessKey 从启用切到停用之后，下一次调用是否立刻被拒。**

为什么这条值得单独写探针：`GetByKey` 是**缓存旁路**（`GetOrAdd(CacheConst.KeyOpenAccess + accessKey, …)`），
所以「停用后立刻失效」天然包含两件事 —— ① 状态闸门 ② 更新时驱逐缓存。
只直接 `UPDATE` 数据库只能验到 ①，验不到 ②；而 ② 一旦漏了，症状是
「运维点了停用、接口还能用，直到缓存过期」，正是最需要自动化守住的那类回归。

探针全程走 `/api/sysOpenAccess/add` 与 `/update`（与运维操作同一条路径），不依赖重启：

| 步骤 | 期望 |
|---|---|
| 新增凭证（status=1, scopes=allocate）→ 签名调用 `/api/pay/status` | 通过认证，拿到业务错误 `[P1004] 收款订单不存在` |
| `/update` 置 status=2（密钥字段**留空**） | 200；且库中密钥**未被改写** |
| **不重启**再调同一接口 | `401 accessKey 无效` —— 状态闸门与缓存驱逐同时生效 |
| 查 `pay_audit_log` | `action=9` 一行，`clientkey` = 该 accessKey，`operatorid=0`，`operatorname=开放接口` |
| 再 `/update` 置回 status=1 → 立刻再调 | 恢复可用（**反证**「停用被拒」不是密钥被写坏） |
| 清空 scopes → 再调 | `401 accessKey 未配置权限范围，拒绝访问（需要 scope=allocate）` |

停用态对外与「accessKey 不存在」**不可区分**（都报 `accessKey 无效`），
不向未授权方泄漏「这个 key 存在但被停用」这一信息。

> ⚠️ **命名澄清（易踩）**：骨架里 `SysLogOp` 与 `SysLogHttp` **不是一回事**。
> - `SysLogOp`（表 `syslogop` / `syslogvis`，配置 `sys_oplog`）是**入站** API 操作日志，由 `LoggingMonitor` 自动落库 ——
>   「谁在何时调了哪个接口」看它。**本项目要复用的就是它**。
> - `SysLogHttp`（表 `sysloghttp`，配置 `sys_http_log`）是**出站** HTTP 调用日志（本项目调用外部接口时才产生），
>   目前业务不调外部 HTTP，因此不会有记录。
>
> 两个开关实测均已开启（`sys_oplog=True`、`sys_http_log=True`）。
> 注意 `SysLogOp` 无前后值字段（`RequestParam` / `ReturnResult` 是请求/响应体），
> 所以「额度从 A 改成 B」这类业务前后值必须另落表 —— 这正是 §9.1 `pay_audit_log` 的职责。

### 9.1 `pay_audit_log` 业务操作审计（F7.3，已确认采用方案 A）

骨架自带的 `CleanSysLogJob` **每天会删除超过保留期的 `SysLogOp` 日志**（保留天数由系统配置
`sys_log_retention_days` 控制），与需求 F7.3「操作日志不可删改」冲突。

**已拍板：单独建表 `pay_audit_log`，只增不删，与 `SysLogOp` 解耦。**

| 字段 | 类型 | 说明 |
|---|---|---|
| Id | long | 主键（`EntityBaseId`） |
| Action | string(32) | 动作：`AccountAdd` / `AccountUpdate` / `QuotaAdd` / `StatusChange` / `AccountDelete` / `AbnormalHandle` / `Export` / **`ApiCall`** / **`ApiAuthFailure`** |
| TargetType | string(32) | 目标类型：`Account` / `Order` / `Abnormal` / **`OpenAccess`** |
| TargetId | long | 目标主键 |
| TargetNo | string(64) | 目标业务标识（账号 Type / 订单号 / accessKey 等，便于检索） |
| BeforeJson / AfterJson | text | 变更前后快照（额度追加等场景便于对账） |
| Remark | string(512) | 说明 |
| OperatorId | long | 操作人（`SysUser.Id`；**系统动作为 0，开放接口调用也为 0**） |
| OperatorName | string(64) | 操作人姓名（开放接口调用固定为「开放接口」） |
| OperatorIp | string(64) | 操作 IP |
| **ClientId** | long? | **调用方（`SysOpenAccess.Id`）**，仅开放接口行为非空。见下方说明 |
| **ClientKey** | string(128) | **调用方身份标识（原始 accessKey）**，让审计行自包含 |
| CreateTime | datetime | 操作时间 |

索引：`(TargetType, TargetId, CreateTime)`、`(Action, CreateTime)`

**为什么 `ClientId` / `ClientKey` 不复用 `OperatorId`**：`OperatorId` 是 `sysuser.id`，
而 `sysopenaccess.id` 是**另一套命名空间**（一个凭证绑定到一个用户，但「调用方」是凭证本身）。
混用会让「按操作人查审计」查出无关行。`ClientKey` 存**原始 accessKey** 是为了让审计行**自包含** ——
凭证行可能被删，认证失败的 accessKey 甚至可能根本不存在于表里。

**两类开放接口审计行**：

| Action | 触发点 | 是否同事务 |
|---|---|---|
| `ApiCall` | `allocate` 建单、`notify` 的每个分支（含幂等命中、订单不存在、已过期、已完结、并发终止、超额到账） | ✅ 与业务变更同事务（`notify` 的重复通知分支除外——它已回滚，用独立连接补记） |
| `ApiAuthFailure` | 签名鉴权失败（`OnChallenge` → `IOpenAccessAuditSink`） | ❌ 独立写入，**必须吞掉所有异常**（审计不可用不能把 401 变成 500） |

> `ApiAuthFailure` **只记带 accessKey 的失败**：匿名请求没有可归属的主体，
> 记下来等于给攻击者一个零成本刷表（而该表只增不删）的放大面。
> 无 accessKey 的失败仍由 `OnChallenge` 的 Warning 文本日志 + `/api/pay/*` 限流覆盖。
>
> `ApiCall` **不为只读的 `/api/pay/status` 记账**：它会被三方轮询，逐次落库会把审计表刷成流水账，
> 反而淹没真正的资金动作。

> 该表**不提供任何 update / delete 接口**，只在业务事务内 append。
> `SysLogOp` / `SysLogDiff` 继续照常记录（保留期清理策略不变），两者职责不同：
> `SysLogOp` 是通用请求级日志，`pay_audit_log` 是业务级不可篡改审计。

**2026-09-17 追加的决策**：

| # | 问题 | 结论 |
|---|---|---|
| 11 | **F6.4「不做脱敏」与「密钥必须脱敏」是否矛盾？** | **不矛盾，两者是不同的东西，不要混为一谈**。F6.4 说的是**收款账号/收款码** —— 调用方必须拿到完整账号才能收款、后台必须能维护，所以不脱敏（§8.3）。而 **`SysOpenAccess.AccessSecret` 是「调用方自己的密钥」**，它在列表页被回显给**只读账号**时没有任何业务价值，只增加泄漏面 —— 所以**必须脱敏**（§8.6.1）。判据：**「调用方拿它去完成业务」→ 不脱敏；「只是展示」→ 脱敏** |
| 12 | 凭证吊销用删除还是停用？ | **停用**（`SysOpenAccess.Status`）。删除会让 `pay_order.ClientId` 与 `pay_audit_log.ClientId` 的引用悬空，历史订单和审计都追溯不到「当时是哪个接入方」—— 对支付系统而言这比「多留一行记录」的代价大得多 |
| 13 | 幂等键的唯一性范围：全局还是按调用方？ | **按调用方**（`(ClientId, ExternalNo)` 复合唯一）。全局唯一会让调用方之间的外部单号互相碰撞：A 用过的 `EX-001` 会让 B 的 `EX-001` 命中 A 的订单，B 拿到的是别人的订单号与完整收款账号 —— 跨调用方串单且双方都看不出异常 |
| 14 | 开放接口的调用审计记在 `pay_order_event` 还是新表？ | **`pay_audit_log` 新增 `ApiCall` / `ApiAuthFailure`**。`pay_order_event` 回答「订单发生了什么」，审计要回答「**是谁**让它发生的」；且认证失败时可能根本没有订单（甚至没有合法的 accessKey），无处可挂 |

> 决策 4 带来一张新表 `pay_audit_log`，其结构见 §9.1。

## 14. 时间基准（接口契约）

> 结论：**本系统的所有时间都是「+08:00（北京时间）墙上时间」，不带时区标记。**
> 这是一个**对外接口契约**，不是实现细节 —— 三方按什么时区传 `notifyTime`，取决于这一节。

### 14.1 现状：四层一致，全部本地时间

| 层 | 做法 | 证据 |
|---|---|---|
| 存储 | `pay_*` 的全部时间列均为 PostgreSQL `timestamp without time zone`（不带时区）。列里存的字面值**就是**显示值 | `information_schema.columns`；守卫 §7o 逐列断言 |
| 写入 | 应用与框架 AOP 全部用 `DateTime.Now`（本地时间） | `PayCenter/**` 无任何 `UtcNow`；`SqlSugarSetup` 给 `CreateTime` 赋 `DateTime.Now` |
| 读入 | MVC 走 Newtonsoft，`DateTimeZoneHandling = Local` → 入参带 `Z` 或 `+08:00` 会被**归一化为本地时间**，不带偏移的按本地解释 | `Startup.cs` 的 `SetNewtonsoftJsonSetting` |
| 输出 | `yyyy-MM-dd HH:mm:ss`，**不带偏移** | 同上 `DateFormatString` |

四者必须**同时成立**才自洽。数据库侧没有任何时间默认值（无 `now()` / `CURRENT_TIMESTAMP`），
所以「当前时间」只有一个来源：应用进程。

### 14.2 对三方的契约

- **推荐**：`notifyTime` 按 `yyyy-MM-dd HH:mm:ss` 传本地时间，例如 `"2026-09-18 09:00:00"`。
- **也接受**：带时区的 ISO 形式（`...T09:00:00+08:00` 或 `...T01:00:00Z`），会被归一化成 +08 后入库。
- **不要**：把北京时间标成 `Z`（`"2026-09-18T09:00:00Z"` 表示的是 UTC 09:00 = 北京时间 17:00，
  会按 17:00 入库）。这不是 bug，是「标了什么就是什么」。
- `notifyTime` 是**可空**的；不传时系统取服务端当前时间。
- 返回给前端的时间字段同样是 `yyyy-MM-dd HH:mm:ss`（无偏移），前端按本地展示即可。

### 14.3 运行时强制：时区不对就拒绝启动

进程时区一旦不是 +08（最常见的是容器默认 UTC），`DateTime.Now` 会变成 UTC 墙上时间、
入参也会被归一化成 UTC，于是**同一列里混入两种含义**（历史行 +08、新行 UTC），
而**不会有任何报错** —— 对账、订单超时判断、订单号日期前缀会全部静默错位。

因此 `PayCenterStartup` 在启动期硬校验，不符合直接抛异常终止进程：

```
✗ 时间基准不符合约定：本进程所在时区不是固定 UTC+08:00。
  → 修复：设置环境变量 TZ=Asia/Shanghai 后重启（容器编排与 systemd 都要设）。
```

- 校验实现：`PayCenter/Const/PayTimeBasis.cs`；挂载点：`PayCenter/PayCenterStartup.cs`
  （放在模块内而非 `Web.Core/Startup.cs`，以保证模块可整体拆出）。
- 同时校验**本年度冬/夏两个时点**都是 +08，以识别「会随季节变化的时区」。
- 部署要求：容器 / systemd / 宿主都要设 `TZ=Asia/Shanghai`；`docker compose` 里显式写 `TZ`。
- 回归：`Admin.NET.Test` 的 `PayTimeBasisTest`（含「守卫必须真的被执行」一条，
  防止守卫被删成空壳而代码看起来正常）。

### 14.4 为什么不改成 UTC + `timestamptz`

- **框架层整体是本地时间**：`EntityBase.CreateTime`（`SqlSugarSetup` 赋 `DateTime.Now`）、
  `CleanSysLogJob`（`CreateTime < DateTime.Now.AddDays(-n)`）、MVC 的 `DateTimeZoneHandling = Local`
  都在框架侧。只把 `pay_*` 改成 UTC，会让**两套基准并存**，比统一本地更危险。
- **迁移是数据改写，不是加个类型**：17 个列从 `timestamp` 改 `timestamptz` 会**重新解释**已有数据
  （PG 按会话时区把字面值当 +08 转成绝对时刻），必须先在备份上验证，属高风险操作。
- **当前没有任何功能收益**：四层一致，端到端正确。

**若将来确实要迁**，需要**成组变更**（守卫 §7o 会在漏改时失败）：

1. `PayTimeBasis` 守卫改为要求 UTC（或直接移除并换一条 UTC 断言）；
2. 写入路径 `DateTime.Now` → `DateTime.UtcNow`（含框架 AOP 覆盖到的 `CreateTime`）；
3. `scripts/paycenter-schema.sql` 增加列类型迁移（`timestamp` → `timestamptz`，含数据改写与回滚方案）；
4. `Startup.cs` 的 `DateTimeZoneHandling` 改为 `Utc`，输出带 `Z`；
5. 前端时间展示改为按 UTC 解析并转本地（`Web/src/views/paycenter/utils/exportParams.ts` 同步调整）；
6. 守卫 §7o 的期望类型与本节一并更新。
